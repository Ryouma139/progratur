「データベース」とひとくくりに言っても、日々の注文処理を支えるDBと、月次の売上分析に使うDBでは求められる性質がまったく違います。この2系統を指す言葉が **OLTP（オンライントランザクション処理）** と **OLAP（オンライン分析処理）** です。何が違い、なぜ多くの現場で両方が必要になるのかを整理します。

## OLTP と OLAP とは

- **OLTP（Online Transaction Processing）**: トランザクションデータを確実かつ効率的に、大量に保存・更新するためのシステム。ECサイトの注文処理や在庫更新、会員登録など「今この瞬間の1件」を正確に処理することが目的。
- **OLAP（Online Analytical Processing）**: 複数のデータソースから集約したデータを様々な角度から分析するためのシステム。売上のトレンド分析や需要予測など「大量データ全体からの意思決定支援」が目的。

## 比較表

| 項目 | OLTP | OLAP |
| --- | --- | --- |
| 目的 | リアルタイムトランザクションの管理・処理 | 大量データの分析による意思決定支援 |
| データソース | 単一ソースのリアルタイムデータ | 複数ソースを集約した履歴・集計データ |
| データ構造 | 正規化されたリレーショナルモデル | スタースキーマ等の多次元（キューブ）モデル |
| データ量 | GB規模 | TB〜PB規模 |
| 応答時間 | ミリ秒単位 | 秒〜分単位 |
| 処理方式 | ストリーム処理（1件ずつのCRUD） | バッチ処理（大量集計） |
| 典型的な処理 | INSERT / UPDATE / 短いSELECT | 大規模なJOIN・GROUP BYを含むSELECT |

応答速度とデータ規模がトレードオフの関係にある点が、この2つを分けて設計する最大の理由です。1件のトランザクションをミリ秒で捌く設計と、ペタバイト規模を横断して集計する設計は、インデックス戦略もテーブル構造も別物になります。

## クエリの傾向の違い

同じ「注文」データでも、OLTPとOLAPでは書くクエリの形が異なります。

```sql title="OLTP: 1件の注文を正確に処理する"
BEGIN;
UPDATE inventory SET stock = stock - 1 WHERE product_id = 1001;
INSERT INTO orders (customer_id, product_id, quantity, ordered_at)
VALUES (2002, 1001, 1, NOW());
COMMIT;
```

```sql title="OLAP: 大量の注文から傾向を分析する"
SELECT
  region,
  DATE_TRUNC('month', ordered_at) AS month,
  SUM(quantity * unit_price) AS total_sales
FROM fact_orders
JOIN dim_store USING (store_id)
GROUP BY region, month
ORDER BY month;
```

OLTP側は「正確さ」と「同時実行時の整合性」（トランザクション、ロック）が主な関心事である一方、OLAP側は「大量データをいかに速く集計できるか」（列指向ストレージ、事前集計、パーティショニング）が主な関心事になります。

## データ構造の違い

OLTPは正規化されたテーブル設計で更新時の不整合を防ぎますが、そのままOLAPの集計クエリに使うと多段JOINが必要になり遅くなります。そのためOLAPでは、事実（売上・数量など）を中心に据えた**ファクトテーブル**と、それを説明する**ディメンションテーブル**（商品、店舗、日付など）に分ける**スタースキーマ**がよく使われます。OLTPで生成されたデータをETL/ELTでOLAP用のスキーマに変換・投入する、という流れが一般的です。

## なぜ両方が必要なのか

全国展開する小売企業を例にすると役割がはっきりします。

- **OLTP**: レジでの商品販売時にリアルタイムで在庫を更新する、顧客アカウントを管理する、支払いを処理する
- **OLAP**: 全店舗の売上動向を分析する、人気商品を特定する、在庫予算を最適化する

OLTPだけでは「今何が売れているか」は分かっても「どの傾向で売上が伸びているか」は分析しにくく、逆にOLAPだけでは注文1件ずつの整合性は担保できません。多くの組織はOLTPで日々のトランザクションを正確に処理しつつ、そのデータをOLAPに集約してBI（ビジネスインテリジェンス）に活用する、という併用構成を取っています。

## AWSにおける対応サービス

| サービス | 位置づけ |
| --- | --- |
| Amazon RDS | OLTP向けのマネージドリレーショナルデータベース |
| Amazon Redshift | OLAP専用のクラウドデータウェアハウス |
| Amazon Aurora | OLTP・OLAP双方のワークロードに対応できるリレーショナルDB |

典型的な構成では、RDS/Auroraでトランザクションを処理し、そのデータをRedshiftに集約して分析する、という役割分担になります。

## まとめ

OLTPは「正確に、速く、1件ずつ」、OLAPは「大量に、横断的に、まとめて」がキーワードです。どちらか一方の技術で両方の要件を満たそうとすると無理が生じるため、システム設計の段階でどちらの特性を優先するデータかを見極めることが重要になります。
