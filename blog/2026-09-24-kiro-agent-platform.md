近年のAIコーディングツールは「エディタの拡張機能」から「開発プロセス全体を担うエージェント基盤」へと役割が広がってきています。その代表例の一つが **Kiro** です。特定のIDEに縛られない設計思想が特徴で、従来型のエディタ拡張とは何が違うのかを整理します。

## 従来型AIツールとの構造的な違い

多くのAIコーディングアシスタントは「エディタのプラグイン」として実装されており、エディタごとに設定・履歴・権限がバラバラになりがちです。Kiroはこれに対し、**UI（IDE / CLI / Web など）とエージェントの処理エンジンを分離する**という設計を取っています。

- 処理エンジン（対話のオーケストレーション、ツール実行、コンテキスト管理、LLM呼び出し）はUIから独立したバックグラウンドプロセスとして動作する
- IDE・CLI・Webなど、どの入り口から接続しても同じコンテキストやルールが適用される
- 端末を閉じても処理が止まらず、クラウド側のセッションから作業を引き継げる

エディタ拡張型の場合、PC上のプロセスに閉じているため「端末を閉じたら止まる」「別のマシンから続きができない」という制約が出やすいのに対し、処理エンジンを独立させることでその制約を回避しているのがポイントです。

## Agent Client Protocol (ACP) という考え方

Kiroは **Agent Client Protocol（ACP）** というオープンな通信規格を採用しています。これは、AIエージェントと開発環境（エディタ）の間のやり取りを標準化するための規格です。

イメージとしては、プログラミング言語の補完・診断機能を各エディタが個別に実装せずに済むようにした **Language Server Protocol（LSP）** の「エージェント版」と捉えると分かりやすいです。LSPが「言語サーバー ⇔ エディタ」の通信を標準化したのに対し、ACPは「AIエージェント ⇔ エディタ」の通信を標準化します。

この標準化のメリットは、特定ベンダーのエージェントが特定IDEに閉じずに済む点です。ACPに対応してさえいれば、サードパーティ製のエディタからでも同じエージェントを呼び出せるようになります。

## 常時稼働エージェントという方向性

もう一つの特徴的な概念が、バックグラウンドやサーバー上で継続的に動く**自律エージェント**（Kiroでは "Crew" と呼ばれる仕組み）です。人が対話的に指示を出すコーディング支援とは異なり、以下のような非同期タスクを人の介在なしに継続実行することを狙ったものです。

- 定期的なログ解析やレポート作成などのスケジュールジョブ
- 要件（仕様）に基づいたタスク分解・実装・テスト・修正のサイクルを、完了まで自律的に繰り返す実行
- システムの状態を定期的に監視し、異常があった場合にのみチャットツールなどへ通知する仕組み

これは「コード補完」の延長ではなく、CI/CDやジョブスケジューラに近い運用寄りの機能として設計されている点が特徴です。

## 運用（Ops）で使う場合に注意すべき考え方

自律的にコマンドを実行できるエージェントを本番環境に近い場所で使う場合、一般的に次のような設計原則が重要になります。

| 観点 | 考え方 |
| --- | --- |
| 実行権限の最小化 | エージェントに与えるコマンド・APIは必要最小限（読み取り専用の監視など）に絞る |
| 実行モードの選択 | 完全自律（自動適用）と、1手ごとに人がレビューする半自律モードを、リスクの大きさに応じて使い分ける |
| 対話型コマンドの回避 | `sudo` や対話プロンプトを伴うコマンドは、非対話環境では正しく動かないため避け、非対話型のスクリプトを用意する |
| 保護対象の明示 | 本番設定ファイルや重要なパスなど、エージェントに変更させたくない範囲を明示的に保護する |

これらは Kiro に限らず、自律的にシェルコマンドやAPIを実行できるタイプのAIエージェント全般に共通する注意点です。「便利だから全自動にする」のではなく、変更の影響範囲が大きい操作ほど人の確認を挟む設計にする、というのが基本的な考え方になります。

## まとめ

Kiroが示している方向性は、AIコーディング支援を「エディタの補助機能」から「UIとエージェント処理を分離した、複数の入り口を持つ開発基盤」へと引き上げる試みだといえます。ACPのような標準規格でエディタとの結合を疎にし、常時稼働のエージェントで開発・運用の非同期タスクまで扱う——という発想は、今後の開発ツールの設計を考えるうえでも参考になる視点です。
